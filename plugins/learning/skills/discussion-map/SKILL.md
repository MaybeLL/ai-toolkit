# Discussion Map

根据对话上下文，运用自己的理解和知识，构建问题本身的逻辑地图。帮助用户看清核心问题、关键概念、相互联系与仍需理解的部分。

对话用于确定问题、背景和关注点。图的组织取决于问题本身的结构，不取决于谁说了什么、追问顺序或某条关系是否被明确说出。

## 触发与上下文

- 只触发 `$discussion-map`（或宿主提供的同名 Skill 入口）就是完整请求。默认理解当前可见对话，直接生成图，无需用户选择节点、关系或格式。
- 用户指定话题或片段时，以指定范围为中心。若当前没有实质讨论，请用户先讨论或提供主题，不用示例图冒充结果。
- 用户提供其他会话 ID 或链接时，使用宿主可用的读取能力获取上下文；无法读取就请求相关内容，不假装看过不可见的历史。
- 默认直接完成理解和绘图，不为了生成关系表或对话引文另行做资料搜集。具体事实若需要核实，按任务需要处理。

## 理解问题与建立关系

- 找到用户真正想理解的核心问题，识别关键概念、子问题以及影响理解的条件。合并不同说法，按问题的内在逻辑重新组织。
- 主动运用理解、推理和已有知识判断联系。可以补出对话没有明确说出的关系和必要的桥接概念，帮助用户形成完整的理解；无需为每条关系寻找对话原句，也不为常规归纳逐条标注「推断」。
- 自行选择适合当前问题的关系，不预设关系清单、节点角色或固定结构。先想清「A 与 B 究竟有什么联系」，再写成简短准确的边标签。确实存在同类关系时允许重复用词；含义过泛时重新检查节点与关系。
- 判断关系是否合理，要看概念含义、适用条件与整体逻辑。既要避免照搬对话中的混淆，也不能把尚未确定的具体事实补成已知结果。只有实质影响理解的不确定关系或假设，才需要条件限定或简短标识。
- 尊重用户当前的问题背景和明确条件；不要因为概念补全而虚构用户的选择、具体实验结果或实际经历。已经修正的背景按当前理解处理，无需回放修正过程。

箭头按「起点＋标签＋终点」读起来应成立，并保持含义清楚；不要把讨论先后当作因果，也不要为使图连通添加含糊的「相关」连线。

## 画清楚

- 默认使用 Mermaid `flowchart`。让结构适合问题，允许跨分支连接；不要强行画成单根树或统一的决策流程。
- 主图用少量关键概念讲清主干。优先合并重复含义、移走旁支；必要时再给主题局部图，保留影响理解的关键区别和限定条件。
- 节点直接写概念或判断，边使用简短而具体的关系词组。不要反复添加「用户认可」「Agent 建议」等发言归属，也不要把长解释放在线上。
- 只在有助阅读时用 `subgraph` 分组。重要的不确定性用文字说明，不只依赖颜色；不要求每张图都有假设、决策、验证或未决节点。
- 使用简单 ASCII 节点 ID 与双引号包裹的中文标签，例如 `Q1["核心问题"]`；避免把段落直接塞进标签。

## 交付与检查

使用用户的语言，默认以 Mermaid 图为主要交付。图前可用一两句点明核心问题；图后只补影响理解的限定或未决点，不重复整张图。

无需附对话依据表、发言归属说明或逐边引文。不要把常规知识整理变成对话追溯报告。

交付前检查：核心问题是否清楚？节点是否抓住关键概念？关系在问题本身是否合理、方向是否正确？必要的隐含联系是否补全？是否引入了无助理解的旁支或未经确认的具体事实？整张图是否能帮助用户形成更清晰的理解？

有现成渲染或语法检查工具时可验证 Mermaid 并修正错误；没有则检查基本语法后交付源码，不声称已渲染验证。仅在用户要求保存文件时写入约定位置。
