# 复杂性与设计判断

本文件用自己的话整理前言、第 1—3、21—22 章及总结中的相关观点；不是原文摘录。末节是 Skill 的应用建议。

## 第 1—3 章：为什么以复杂性衡量设计

软件设计贯穿开发和维护过程，初始方案需要随实践修正。复杂性指完成开发任务时理解和修改系统的困难程度，不等于功能多、系统大或代码长。可以消除不必要的复杂性，也可以把不可避免的复杂性封装起来，使多数使用者不必接触它。

第 2 章区分三种症状：一次需求变化需要修改许多位置（变更放大）；完成任务必须记住大量规则（认知负荷）；甚至不知道还需要检查哪些条件或模块（未知的未知）。主要原因是依赖与模糊性。依赖无法完全消除，但可以使其范围更小、更明确。

复杂性的影响与开发者接触相关代码的频率有关。把困难集中在一个稳定、接口清楚的实现内部，可能比把简单片段分散给所有调用者更好。读者的困惑也是证据，不能仅以作者已经熟悉代码来判断它简单。

第 3 章主张持续投入设计，避免每次只增加一个补丁、最终积累大量隐含规则。投入包括比较方案、补充关键说明和修正已暴露的抽象问题，不是提前设计所有未来需求。书中的投入比例与回报时间属于作者建议和估计，不是通用配额或经过验证的收益承诺。

## 第 21—22 章：识别重要信息，回到总体目标

重要性取决于任务和约束。能解释多种行为的不变量、支持多个用例的操作、必须满足的性能条件，往往比单次操作的实现细节更值得突出。让这些信息出现在接口、名称或核心结构中，其余细节尽量局部化。

两种失败都要避免：暴露过多无关细节，使所有调用者承担学习成本；隐藏真正重要的条件，使调用者无法正确使用。第 22 章与总结回到同一目标：通过反复设计和反馈减少理解、修改的负担。前言强调，具体原则若没有降低复杂性，就不应机械坚持。

## 用于当前任务

从一条真实变化追踪影响范围，再说明是哪种症状、由什么依赖或缺失信息造成。结合使用频率、变化概率和故障后果选择处理重点；不要把书中的定性描述变成一个伪精确的复杂性分数。

例如（自拟）：多个导入入口各自实现日期格式规则，改格式时容易漏改。可比较集中解析与保留各入口解析；若各入口实际采用不同的日期语义，强行统一反而会掩盖差异。
