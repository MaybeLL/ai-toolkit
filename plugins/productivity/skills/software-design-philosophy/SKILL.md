# 软件设计的哲学

让软件更容易理解和修改。以系统整体及常见开发任务的成本判断设计，而非代码行数、类数量或模式名称。模块可以是函数、组件、库、服务或子系统。

## 判断依据

结合当前目标、已有代码或代表性使用场景，识别三种复杂性：一个变化牵动多处修改；完成任务必须记住许多细节；必要的规则或依赖难以发现。追踪其原因，优先处理经常使用、经常变化或后果严重的部分。

- **深模块**：在简单而完整的接口后封装丰富功能及实现复杂性。接口成本包含调用规则、配置、错误与生命周期，不只看参数数量。
- **信息隐藏**：让实现知识有清晰归属，隔离可能变化的决策。合并或拆分的依据是知识共享与独立理解能力；相似代码不一定代表相同概念。
- **适度通用**：用自然的通用操作覆盖当前需求，分开机制与用例策略。新增抽象应减少实际负担，而非预建尚无需求的扩展框架。
- **承担复杂性**：由掌握相关知识的模块完成共通工作，使常见用法容易。必须由调用者决定的策略和影响正确性的语义仍需公开。
- **减少特殊情况**：优先寻找能统一处理边界状态的定义；恢复失败或结果未知不能伪装成成功。
- **表达重要信息**：名称、类型与简洁注释应让使用者无需推测实现就能正确使用。记录缺失的语义和原因，不复述代码。

这些原则用于比较方案。若应用某条原则增加了总体负担，就调整方案；危险信号本身不是设计缺陷的证据。

## 融入当前任务

**设计和实现**：先明确关键行为与契约。重要且有取舍的决策比较实质不同的方案，再选择调用负担、实现成本和约束更合适的一种。

**修复和重构**：从可复现问题或现有行为出发，检查能否改善局部抽象，避免不断叠加特例。结合兼容性和工期选择改动范围，并验证相关行为。小改动不必扩大成设计项目。

**评审**：将判断落到具体代码和使用情境，说明造成的影响、建议及代价；区分功能错误、设计风险与个人偏好。信息不足时标明待核实项，没有实质问题时直接说明。

沿用项目的语言惯例、测试流程和用户约束，包括 TDD。结论与交付形式随任务调整，不要求额外报告、固定表格或章节引用。
