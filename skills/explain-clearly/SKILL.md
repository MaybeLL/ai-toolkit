# Explain Clearly

让读者一次读完就形成正确的整体认识，并能用自己的话复述核心逻辑。

## 定位与触发

- 仅在用户显式输入 `/explain-clearly` 时生效，是一种通用的解释风格，不限定主题深浅。
- **一次一个主题**：同属一个主题的复合问题（如"X 是什么、和 Y 有什么区别"）视为一个问题正常回答；不相关的多个主题逐个依次回答，每个都走完整骨架，不丢弃用户的任何问题。
- 输出语言跟随用户提问的语言。

## 读者契约

读者是**智力健全的外行**：不缺理解力，只缺这个领域的背景。

- 不依赖未解释的领域黑话。每个领域术语**第一次出现**时用一句白话锚定，之后可正常使用。
- 不降低内容精度，不用幼儿化的口吻。

## 输出骨架

顺序契约固定，呈现自由（不强制小节标题，简单问题可以是几段流畅的话）：

1. **结论先行** — 第一句话直接回答问题
2. **整体图景** — 它解决什么问题、由什么组成、如何连接
3. **关键点** — 理解所必需的逻辑环节
4. **图 / 表 / 例** — 按下方分派规则
5. **一句话收束** — "所以……"点出核心因果，不复述内容

### 结构预算

难读的根源是长段落和要点膨胀，用结构约束而非字数约束：

- 关键点最多 **4 个**，每个 **1–3 句**
- 每个段落不超过 **3 句**
- 问题过于复杂时只解释主干，并明确指出省略了哪些分支

### 图与表：按问题类型分派

| 问题类型 | 形式 |
|---|---|
| 机制 / 流程 / 架构（"如何工作""由什么组成"） | **必须**画 ASCII 草图 |
| 对比（"X 和 Y 有什么区别"） | 用小表格 |
| 权衡 / 原因（"为什么这样设计"） | 可无图；若存在因果链（A 导致 B 导致 C）则鼓励画出 |

质量底线：**图必须承载正文没有的压缩信息**（关系、顺序、层级、数据流）。画不出增量信息就不画——禁止装饰性画图。

### 坍缩规则

骨架永远成立，但任何**没有增量信息的环节坍缩或省略**：

- 一句话结论已完整回答问题时，整体图景与关键点可合并为一段或省略
- 正文少于三段时，省略收束句

简单问题的输出自然退化为"直接答案 + 一个例子"。这与禁止装饰性画图是同一条原则：不承载信息的形式一律删掉。

## 例子协议

- **首答优先最小真实例子**：来自该领域内部的、最小可运行/可观察的实例（一行代码、一条命令、一个真实输出），而非生活类比。
- **类比是第二回合的补救手段**：仅当用户反馈没看懂时切换为生活类比，且类比必须与原机制精确同构，并注明它在哪里失效。

## 黄金示例

以下是本 skill 的目标形态（机制类、中等复杂度）：

> **问：DNS 是怎么把域名变成 IP 的？**
>
> DNS 是一套分层的查询系统：浏览器拿着域名逐级问下去，直到问出负责该域名的服务器，由它给出 IP。
>
> 你的电脑并不直接认识所有域名。它把问题交给递归解析器（一台代替你跑腿查询的服务器，通常由运营商提供），由它逐级查询：
>
> ```text
> 浏览器 → 递归解析器 → 根服务器       "谁管 .com？"
>                     → .com 服务器    "谁管 example.com？"
>                     → 权威服务器     "IP 是 93.184.216.34"
> ```
>
> 每一级都不知道最终答案，但知道该问谁——只负责指路，系统因此不需要一台无所不知的服务器。同时每级结果都会被缓存，多数查询根本走不到根服务器。
>
> 试试在终端运行 `dig example.com`：输出的 ANSWER 段就是权威服务器给出的 IP，TTL 字段是它允许被缓存的秒数。
>
> 所以 DNS 又稳又快，靠的不是一台中心服务器，而是分层指路加层层缓存。

注意：图的形式（流程、层级、表格）随问题类型变化，勿套用本例的样式。
